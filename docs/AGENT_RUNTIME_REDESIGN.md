# 对话式 Agent Runtime 重构说明

> 日期：2026-09-21
>
> 目标：解决“LLM 只做首次格式化、后续流程像脚本、当前状态与历史记录互相矛盾”的问题。

> 状态：核心数据结构、对话命令和界面已实现；后续增加经确认的任务字段修改，自动化 47 / 47 通过，并已用隔离 store 完成真实模型对话及桌面、390px、320px 浏览器复核。十套人工对话样本尚未全部执行。

## 1. 已确认的问题

当前实现把三类数据混在同一个结果页：

- 模型首次分析得到的 `follow_ups`；
- 状态机生成并由用户回答的澄清问题；
- 任务创建后的追踪汇总和事件日志。

它们没有共享生命周期，因此会出现：

- 澄清已经完成，首次分析的“待确认事项”仍继续显示；
- “已确认的澄清”和“待确认事项”描述的是同一问题，却分开呈现；
- 任务状态改变没有独立事件，用户只看到随后触发的追踪结果；
- 任何任务统计变化都可能重复生成“发现逾期”，没有任务名、截止日期和变化原因；
- 文档定义了 7 个 Prompt Skill，但当前模型只实际参与首次抽取、完整性和优先级判断。

## 2. 产品定义

重构后的产品仍是状态机驱动的单 Agent，但交互入口和运行记录统一：

```text
用户自然语言 / 页面快捷操作
            ↓
       Agent Runtime
            ↓
  意图理解与行动计划（需要语义判断时调用 LLM）
            ↓
  状态机、权限和参数校验（确定性代码）
            ↓
  写操作前人工批准 / 明确用户命令
            ↓
       工具执行与回读
            ↓
  事件账本 + 当前状态 + Agent 回报
```

聊天窗口不是 Agent 的定义。Agent 属性来自持续上下文、意图判断、工具选择、受控执行、结果验证和解释性回报。日期计算、权限校验、幂等和回读必须继续使用确定性代码，不能交给模型猜测。

## 3. 职责边界

| 层级 | 负责 | 不负责 |
|---|---|---|
| LLM | 纪要理解、自然语言意图、歧义判断、行动说明、结果总结 | 权限绕过、日期真值、幂等、最终写入结果 |
| Agent Runtime | 组合上下文、选择允许的命令、组织工具结果、生成对话回报 | 直接修改未经校验的数据 |
| 状态机 | 阶段守卫、审批要求、允许的状态转换 | 自然语言含义判断 |
| 规则引擎 | 日期、逾期、字段校验、状态跃迁判断 | 冒充 Agent 解释或重复生成汇总消息 |
| Connector | 创建、查询、更新外部任务 | 决定业务意图或跳过审批 |

## 4. 权威运行数据

### 4.1 OpenItem

所有当前需要用户处理的问题使用同一结构，不再把模型初始 `follow_ups` 直接当作永久待办：

```ts
type OpenItem = {
  id: string;
  kind: "clarification" | "follow_up";
  status: "open" | "resolved" | "dismissed";
  task_id: string | null;
  question_id: string | null;
  prompt: string;
  answer: string | null;
  resolution: string | null;
  created_at: string;
  resolved_at: string | null;
};
```

普通界面只展示 `status=open`。已解决内容进入历史，不再同时出现在“待确认”中。运行时 `analysis.follow_ups` 与当前未解决事项同步；模型原始 `follow_ups` 保留在 `analysis_trace.model_output` 中。审批是单独的受控工作区，当前未建模为 `OpenItem` 类型。

### 4.2 DomainEvent

所有有业务意义的改变必须写入事件账本：

```ts
type AgentEvent = {
  id: string;
  type: string;
  actor?: "user" | "agent" | "system" | "tool";
  source?: "runtime" | "chat" | "quick_action" | "model" | "connector";
  entity_type?: "run" | "task" | "open_item";
  entity_id?: string;
  message: string;
  before?: Record<string, string | number | boolean | null>;
  after?: Record<string, string | number | boolean | null>;
  at: string;
};
```

当前覆盖：分析完成、提出问题、回答问题、批准、创建、回读、状态改变（包括任务开始）、首次逾期、完成和失败。截止日期调整只允许在审批前编辑计划；已创建任务的截止日期变更不是本轮能力，不能声称有独立事件。

### 4.3 ConversationMessage

对话记录保存用户消息、Agent 回报和操作摘要。页面快捷操作经 `AgentCommandSchema` 派发；自然语言消息先由 LLM 规划受限意图，再由服务端执行或提出状态变更待确认操作。来源分别记录为 `quick_action` 或 `chat`。模型规划的系统提示、上下文和原始输出保存在 `model_interactions`，可以在运行检查器查看。

## 5. 触发规则

- 状态改变：每次成功改变任务状态都记录任务名、旧状态、新状态和来源。
- 逾期：仅在任务从“未逾期”跨入“逾期”时产生事件；包含任务名、截止日期和逾期天数。
- 重复刷新：如果没有状态跃迁，不新增追踪业务事件，只更新 `checked_at`；用户主动刷新仍会产生一组对话请求 / 回报，用于解释检查结果。
- 完成：最后一个任务完成后产生任务完成事件和运行闭环事件。
- 澄清：答案提交后，对应 OpenItem 立即变为 `resolved` 或 `dismissed`。
- 对话更新状态：必须先解析到唯一任务和合法目标状态；含糊时先提问，不能猜任务。

## 6. 页面信息架构

普通用户工作区只展示四类内容：

1. **Agent 对话**：当前结论、问题、用户命令、执行结果和下一步。
2. **当前任务**：每项任务最新且唯一的权威状态。
3. **待处理事项**：只展示仍为 `open` 的问题或审批。
4. **活动时间线**：按时间展示完整业务事件及关联任务。

Prompt、原始模型 JSON、归一化数据和 Skill 快照继续放在运行检查器中，不与业务时间线混排。

## 7. 信息密度原则

- 工作区正文和交互控件不使用难以阅读的微小字号；正文目标不低于 12px，辅助文字不低于 10px。
- 缩减结果区、面板和列表之间没有信息意义的大段留白。
- 任务状态、待处理事项和活动记录优先使用紧凑的纵向信息流，不用大卡片包裹少量文字。
- 桌面、390px 和 320px 均需验证无文字遮挡、无横向溢出、操作按钮可访问。

## 8. 最小验收场景

1. 含糊纪要生成 3 个 OpenItem；回答后 3 个都进入已解决历史，当前待处理数量为 0。
2. 模型首次输出的 `follow_ups` 不再在澄清完成后作为当前待确认事项展示。
3. 用户点击或在对话中要求“开始任务”，均生成明确的状态改变事件和 Agent 回报。
4. 一个已逾期任务从待开始改为进行中，只记录状态改变；不会再次生成相同逾期事件。
5. 首次跨入逾期时记录任务名、截止日期和逾期天数；重复刷新不新增事件。
6. 含糊的自然语言状态命令必须要求用户选择任务，不能误改。
7. 未经批准不能创建任务；连接器结果必须回读后才能显示成功。
8. 刷新页面后，对话、OpenItem、任务状态和事件时间线保持一致。
