## 1. 先读结论

本项目不是“把纪要总结一下”的页面，而是要完成以下受控闭环：

```text
会议纪要
→ 行动项识别
→ 信息完整性判断
→ 主动澄清
→ 任务规划
→ 人工批准
→ 创建任务
→ 回读验证
→ 状态追踪
→ 完成闭环
```

当前真实状态：

- 前端主流程已切换到 `/api/agent/runs`，并通过浏览器保存的 `runId` 在刷新后恢复服务端运行。
- 用户侧分析为 API-only：未配置、调用失败或结构化输出无效时显式报错，不静默降级；本地规则函数仅用于确定性测试。
- 页面保存的模型配置持久化到被 Git 忽略的 `data/model-config.env`，跨服务重启保留；当前属于本机单用户原型密钥存储。
- 分析、对话式澄清、统一审批、执行日志、逐字段回读验证、任务追踪和完成 / 失败状态均有前端界面。本轮又增加可输入的 Agent 对话、统一待处理事项与活动时间线，并在隔离运行中完成端到端浏览器复核。
- 用户上下文已切换为一个或多个可编辑的 Markdown Skill，并在每次运行中保存快照。
- 分析与流程规则已拆成 9 个版本化 Prompt Skill，运行记录会保存版本号。分析请求实际注入抽取、完整性和优先级 3 个模块；对话请求注入 `dialogue-orchestration` 与 `task-editing`。其余流程规则由确定性状态机实现，不能声称 9 个模块都逐一调用模型。
- 任务已包含 `priority_reason`、`priority_evidence` 和结构化 `priority_conflict`，冲突先澄清，审批页仍可调整优先级并查看理由。
- 外部写操作仍须显式人工批准；批准任务使用幂等键创建，并在进入追踪前回读验证。
- 本轮自动化测试为 2 个文件、47 个用例，均已通过；生产构建通过（2026-09-21）。
- 真实飞书、Trello、Notion 等连接器不属于当前中期阶段交付；使用本地持久化连接器跑通完整闭环。

任何后续说明、报告和演示都必须遵守以上事实，不得把 `Local Task Hub` 表述为真实第三方平台，也不得用当前测试替代真实业务准确率评测。

## 2. 项目定位

这是一次项目制作训练，不是毕业设计或纯学术研究，但开发、测试和文档应参考企业项目标准。

产品名称尚未最终确定。对外材料优先使用：

- 本项目
- 本系统
- 会议行动智能体
- 会议纪要转任务系统

不要围绕 `Minutes` 或 `Meeting Action Agent` 建立固定品牌叙事。它们只是当前界面和仓库中的暂定名称。

开题或中期材料不应反复区分“已实现 / 未实现”，但工程交接文档必须如实区分，以便开发和验收。

## 3. 为什么它需要 Agent

普通 NLP 或单次大模型调用只能完成：

```text
会议文本 → 结构化任务列表
```

本项目的 Agent 属性来自：

1. 保存一次会议处理的上下文和状态；
2. 判断任务信息是否足够；
3. 信息不足时主动提问，并将回答和未解决事项保持在同一生命周期；
4. 根据回答更新原任务，而不是无状态重跑；
5. 在外部写操作前等待人工批准；
6. 调用工具创建任务；
7. 回读目标系统并验证字段；
8. 持续追踪直到完成或失败，并记录任务状态跃迁及首次逾期；
9. 在对话中理解自然语言意图，经过状态守卫和必要的人工确认后执行允许的操作并回报结果。

答辩中的准确说法是：本项目采用**状态机驱动的单 Agent / 工作流型 Agent 架构**。它不是高度自主的通用 Agent，但更适合涉及外部写操作的企业流程。

不要为了显得“更像 Agent”强行拆成多 Agent。当前场景边界清晰，多 Agent 会增加状态同步、调用成本和调试难度。

## 4. 状态机、Prompt Skill 与用户上下文的关系

三者必须分层：

### 4.1 状态机：控制流程和权限

当前后端状态：

```text
analyzing
→ clarifying
→ awaiting_approval
→ executing
→ verifying
→ tracking
→ completed / failed
```

状态机决定“现在在哪一步”和“下一步允许做什么”。例如：

- 有必填信息缺口时不能创建任务；
- 没有用户批准时不能进入执行；
- API 返回成功后仍必须进入验证；
- 验证失败不能显示为成功；
- 所有任务完成后才能进入 `completed`。

### 4.2 项目 Prompt Skill：规定每一步如何判断

项目已实现类似 Skill 的版本化提示词，当前阶段不进行模型微调。

当前拆分为 9 个版本化 Skill；`meeting-extraction`、`priority-reasoning` 和 `dialogue-orchestration` 为 `1.1.0`，其余为 `1.0.0`：

- `meeting-extraction`：识别任务、决策、风险和原文证据；
- `completeness-check`：判断负责人、日期、交付物、验收标准是否缺失；
- `clarification`：只提出必要问题，优先给可选答案；
- `task-planning`：拆分任务、处理依赖、选择创建字段；
- `priority-reasoning`：给出优先级、理由和证据；
- `verification`：比较源任务与回读任务，判断是否一致；
- `tracking`：识别逾期、阻塞和完成状态。
- `dialogue-orchestration`：根据运行上下文规划澄清回答、进度查询、状态变更提案、任务字段修改和解释；
- `task-editing`：定位唯一任务、仅提议明确字段变更，要求用户确认和完整日期。

定义集中在 `server/prompt-skills.ts` 并进入版本控制。每次运行把完整版本映射写入 `skill_versions`，关键事件也记录对应 Skill 元数据。分析系统提示组合抽取、完整性和优先级规则；对话系统提示组合对话编排与任务编辑规则。澄清字段更新、审批、验证和追踪的安全边界由确定性代码执行，版本登记不等于模型调用。会议纪要、用户 Markdown Skill 和补充要求都是待分析数据。

只有当项目积累了足量且稳定的“纪要 → 人工修正 → 最终任务”标注数据后，才评估微调。现阶段微调不利于快速迭代，也难以解释错误来源。

### 4.3 用户 Markdown Skill：提供团队专属知识

用户可以创建一个或多个独立 Markdown 文件，用自然语言描述任何对会议理解有帮助的知识，例如成员别称、角色、项目术语、优先级习惯、会议类型要求、交付物格式和验收习惯。系统只管理文件名、启用状态和版本元数据，不解析正文中的固定字段，也不要求用户按表格填写。

启用的 Markdown 正文会作为待分析业务资料注入模型 Prompt，并随运行保存快照。它只能补充业务含义，不能改变系统 Prompt Skill、人工审批、安全规则或工具权限。用户 Skill 不能通过文字要求跳过审批、伪造完成或执行未授权工具操作。

旧版 `TeamContext` 结构仅保留在服务端迁移和历史确定性测试辅助中，不属于用户侧分析 API，也不应再作为新功能的依赖。模型输出仍必须是结构化 JSON，因为状态机、澄清、审批、任务创建和回读验证需要明确字段；这不意味着用户输入必须结构化。

## 5. 优先级设计决定

不要为每条任务增加一次独立的优先级问答，否则会造成澄清疲劳。

正确流程：

1. 模型先给出 `priority`；
2. 同时给出 `priority_reason` 和 `priority_evidence`；
3. 用户在统一审批界面中调整；
4. 只有出现以下情况时才主动澄清：
   - 原文同时出现相互冲突的紧急程度；
   - 高优先级没有任何原文依据；
   - 优先级会与截止时间或依赖关系产生明显冲突；
   - 用户的团队优先级规则与模型判断冲突。

当前 `TaskSchema` 已加入可解释字段：

```ts
priority_reason: string;
priority_evidence: string | null;
priority_conflict: boolean;
```

API 模型结果在进入状态机前还会执行一个窄范围的原文冲突守卫：当任务证据、标题或描述同时出现高优先级与低优先级信号（例如“紧急”与“可选”）时，系统强制归一为 `medium`、清空单一证据并标记 `priority_conflict=true`，等待人工确认。该守卫只检查模型已经返回的任务文本，不解析用户 Markdown Skill，也不新增结构化用户配置字段。

## 6. 当前技术架构

```text
React + TypeScript + Vite
          │
          │ HTTP / JSON
          ▼
Node.js + Express + TypeScript
          │
          ├─ OpenAI-compatible model client
          ├─ Zod schema validation
          ├─ Agent state machine
          ├─ JSON persistent store
          └─ TaskConnector
               └─ Local Task Hub（当前）
```

技术栈：

- 前端：React 19、TypeScript、Vite、Phosphor Icons、HLS.js；
- 后端：Node.js、Express 5、TypeScript；
- 模型：OpenAI-compatible Chat Completions；
- 结构校验：Zod；
- 当前持久化：`data/agent-store.json`；
- 当前任务工具：`Local Task Hub`；
- 测试：Vitest。

## 9. 已实现能力与验证边界

### 产品能力

- 粘贴会议纪要；
- 导入 TXT / Markdown；
- 首页提供一份综合测试纪要，同一次演示覆盖完整抽取、模糊澄清、成员别名、优先级冲突、依赖风险与非任务识别；独立回归用例仍按功能拆分；
- 输入会议日期和补充要求；
- 提取会议标题、摘要、参会人、决策、任务和待确认项；
- 提取任务负责人、日期、优先级、状态、依赖、风险、证据和置信度；
- 用户在审批中编辑任务字段并选择实际创建范围；
- Markdown / CSV 导出；
- API-only 模型分析；未配置或调用失败时显式报错；
- DeepSeek / OpenAI-compatible API 配置；
- 测试、保存和清除模型连接；
- 创建或恢复有状态 Agent 运行；
- 对话式澄清及逐题历史；
- 统一审批、部分批准、字段编辑和优先级理由；
- 执行轨道、工具日志、回读验证、失败提示和幂等安全重试；
- Local Task Hub 外部 ID、状态更新、逾期统计和完成闭环；
- 对话输入可询问运行情况、回答当前澄清问题、请求刷新追踪、提出唯一任务的状态变更，或在审批前 / 追踪中提议修改标题、描述、负责人、截止日期和优先级。写入均需再次确认；模糊目标和不完整日期不会执行；
- `open_items` 仅展示当前未解决问题，已答澄清进入历史；原始模型输出与对话模型交互保留供检查；
- 检查器使用单一正文滚动区，标题与分类标签固定在弹窗内；澄清、优先级及任务状态选项使用可键盘操作的非模态单选菜单，展开时不隐藏页面滚动条；
- 状态改变记录任务名称、前后状态和来源；首次发现逾期记录任务名称和截止日期，重复刷新不重复生成同一逾期事件；
- 用户 Markdown Skill 中的成员别名 / 角色、术语、时区、优先级规则和自定义指导；
- 桌面端和移动端重新编排的工作区与配置弹层。
- 滚动时常驻的顶部导航栏，以及不被导航遮挡的页面锚点。

“对话调用”只由运行中的聊天框提交自然语言消息触发：`POST /api/agent/runs/:id/messages` 使用 `dialogue-orchestration` 和 `task-editing` 调用模型规划意图，成功解析后把系统提示、上下文输入、原始输出和归一化意图写入 `model_interactions`。初次会议分析是单独的模型调用，显示在“模型输出”；表单澄清、审批、任务状态快捷控件、追踪刷新与确认提案通过状态机执行，不新增对话模型调用。调用失败不会产生 `model_interactions` 记录，前端显示错误。

### Agent 闭环验证

本轮在独立临时 store 中使用真实 DeepSeek 从含糊纪要走到闭环：模型提出 9 项澄清，分批解决 / 否认后当前待处理为零；批准 1 项得到 `LTH-*` ID 且回读一致。页面将任务标记进行中后，自然语言“开始吧”只触发追问，明确完成请求先提议、确认后才写入并进入 `completed`；检查器可查看两次对话的模型输入和输出。桌面、390px、320px 均已复核，无横向溢出或浏览器错误。自动化测试另外覆盖首次逾期与旧运行迁移：

```text
创建运行（clarifying）
→ 回答 3 个信息缺口
→ awaiting_approval
→ 批准创建
→ Local Task Hub 返回 LTH-... ID
→ 回读字段验证通过
→ tracking
→ 把任务标记完成
→ 刷新追踪
→ completed
```

同一次运行重复或并发审批会复用已有记录，不产生重复任务；审批前追踪、计划外任务注入、非法日期、非法确认值、保留键 ID、损坏 JSON 和超大请求均会被拒绝。逐项结果见 `docs/ACCEPTANCE_RESULTS.md`。

另一次隔离的合成运行验证了对话字段编辑：真实模型面对“把任务3的截止日期改成2027年”要求补全月日，没有提案或写入；给出完整 `2027年1月31日` 后展示原值与新值，经用户确认才更新 Local Task Hub，回读与事件一致。这只覆盖该条语义路径，不代表全部对话样本通过。

## 17. 答辩口径

### 项目真正的技术难点

会议纪要表达不规范，同一句话可能同时包含决策、任务和风险，负责人和相对日期还经常被省略。技术上需要让模型稳定输出可验证的结构化数据，并用规则、Zod 校验和原文证据降低错误传播。

不要强行把“创建后回读”说成唯一难点；它是可靠性设计的一部分。

### 为什么采用状态机

状态机把工作分成分析、澄清、审批、执行、验证和追踪阶段，并限制每个阶段允许的操作。它防止 Agent 跳过澄清或审批，也让失败恢复和过程展示更清楚。

### 架构是否符合当前 Agent 做法

符合业务型 Agent 的常见做法：大模型负责理解与判断，状态机控制流程，工具负责执行，人工审批控制风险。它属于工作流型 Agent，而不是通用自主 Agent；这是针对业务可靠性的主动选择。
