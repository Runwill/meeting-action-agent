# 会议纪要转任务系统中期报告

> 报告日期：2026-09-21
>
> 交付范围：除真实第三方任务平台接入外的中期可运行版本

## 1. 项目概述

本项目面向中文会议后的行动落实场景，将非结构化会议纪要转换为可澄清、可审批、可验证、可追踪的任务。系统不是一次性摘要工具，而是采用状态机驱动的单 Agent / 工作流型 Agent 架构，把用户配置的模型 API 理解能力与确定性的流程控制结合起来。内部规则函数仅用于自动化测试，不作为用户侧分析模式。

中期原型的受控闭环如下；本轮又将自然语言对话、当前待处理事项和业务事件接入同一运行：

```text
会议纪要
→ 行动项识别
→ 完整性判断与主动澄清
→ 统一人工审批
→ Local Task Hub 创建任务
→ 逐字段回读验证
→ 状态追踪
→ 全部完成后闭环
```

中期演示使用本地 `Local Task Hub` 作为任务平台替身，用来验证 Agent 的工具调用、幂等、回读和追踪；飞书、Trello、Notion 等真实第三方平台属于下一阶段。

## 3. 系统架构

```text
React 19 + TypeScript + Vite
        │
        │ HTTP / JSON
        ▼
Express 5 + TypeScript
        │
        ├─ Agent 状态机与状态守卫
        ├─ OpenAI-compatible Chat Completions（用户必须配置）
        ├─ Prompt Skill（分析与对话按阶段注入）
        ├─ Zod 输入与结构校验
        ├─ JSON 运行与任务存储（Skill 文件独立保存）
        └─ TaskConnector
             └─ Local Task Hub（中期版本）
```

状态机包含：

```text
analyzing
→ clarifying
→ awaiting_approval
→ executing
→ verifying
→ tracking
→ completed / failed
```

状态机负责决定当前允许的动作。缺少必要信息时不能创建任务，未批准时不能执行写操作，创建成功后必须回读，数量或字段不一致时不能进入正常追踪。

## 4. 核心实现

### 4.1 分析与正确澄清

系统使用用户配置的 OpenAI-compatible 模型 API。模型输出经 Zod 校验；模型未配置、调用失败或结构化输出无效时直接返回明确错误，不生成本地规则替代结果，也不返回 API Key 或供应商错误原文。内部本地规则函数只为确定性单元测试提供输入基线。

模型抽取后会经过 Schema 校验，并结合启用的用户 Markdown Skill 理解团队称呼和业务规则。负责人、截止日期缺失时会提问；低置信度候选任务会要求确认；原文信号、Skill 规则或两者互相冲突时会要求人工选择最终优先级；零任务结果会进入补充信息流程。每个答案只修改关联字段，用户否认的候选任务会被移除，并保留澄清历史。

### 4.2 审批、执行与验证

审批页允许选择任务范围、编辑任务字段和调整优先级。后端要求审批载荷与本次运行的原计划任务集合一致，拒绝注入计划外 ID；只有被选中的任务会创建，且进入连接器时状态强制为 `todo`。

每个任务使用稳定幂等键。相同审批重复或并发提交会复用已有 `LTH-*` 任务，不会重复创建；JSON store 的首次加载也复用同一读取 Promise，避免冷启动双重执行。失败运行可用完全相同的原审批载荷再次调用 `/approve`；审批签名不一致会返回 `409`。创建后系统逐字段回读标题、描述、负责人、日期、优先级、理由、证据、状态、依赖和风险，任一关键字段不一致即进入 `failed`。

### 4.3 追踪与恢复

只有本次运行中已经批准且验证通过的任务可以进入追踪。追踪统计包括待开始、进行中、已完成和逾期数量。页面快捷操作和自然语言状态请求都进入受控 Agent 命令路径；自然语言状态请求先产生待确认提案，用户二次确认后才写入。状态改变事件包含任务名、前后状态和来源，首次发现逾期的事件包含任务名、截止日期及逾期天数；无变化的重复刷新不再产生相同逾期事件。所有已批准任务完成时运行进入 `completed`，完成态不再允许修改任务状态。

前端在 `localStorage` 中仅保存最近一次运行 ID，不保存会议正文或 API Key。刷新时使用 `GET /api/agent/runs/:id` 恢复服务端持久化状态。

### 4.4 对话、当前事项与活动记录

每次运行保存用户输入、Agent 回报和最近的对话上下文。模型只负责把自然语言规划为受限意图：回答当前澄清、刷新追踪、提出唯一任务的状态变更、提出任务字段修改、解释或要求补充。字段修改覆盖标题、描述、负责人、截止日期和优先级，可在审批前或追踪中提出；界面展示旧值与新值，用户确认后才更新，追踪中的 Local Task Hub 更新还需回读。后端继续验证问题 ID、任务归属、运行阶段、目标状态及完整日期；模型不能直接执行写操作。澄清答案会关闭关联的 `open_items`，旧模型 `follow_ups` 不再作为独立的永久待办显示。页面展示当前未解决事项和业务事件时间线；原始纪要、模型输出、Prompt 与 Skill 快照仍可在运行检查器中核对。旧运行通过迁移从问题和澄清历史恢复事项状态，不把已答问题重新打开。

### 4.5 用户 Markdown Skill

用户可创建多份独立 Markdown 文档，自然语言描述成员称呼、术语、优先级习惯和会议类型要求。正文不被产品代码解析为固定字段，而是作为业务资料注入模型提示；启用状态、文件名和正文会在运行中保存快照，检查器可查看实际输入。旧版结构仅保留迁移和确定性测试兼容，不是用户侧分析模式。用户 Skill 不能覆盖审批、安全、输出校验或工具权限。

### 4.6 Prompt Skill（模型可见的两组规则）

| 使用场景 | 注入的规则 | 用途 |
|---|---|---|
| 会议分析 | 任务提取、完整性检查、优先级解释 | 从原文提取任务，识别缺失信息，并给出可追溯的优先级理由 |
| 运行内对话 | 对话编排、任务编辑 | 识别查询/澄清/修改意图，生成受限提案并等待确认 |

审批、验证、追踪等规则由状态机和工具守卫执行，不是额外的模型功能。系统提示明确规定会议纪要和用户 Markdown Skill 均为待分析数据，不能改变审批要求、输出结构或工具权限。

## 5. 数据与 API

核心运行记录包含状态、分析结果、待回答问题与 `open_items` 生命周期、澄清历史、批准范围、外部任务映射、追踪汇总、业务事件、对话、待确认状态操作、Prompt Skill 版本、用户 Markdown Skill 快照、实际 Prompt / 模型输出和原始输入。

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/agent/runs` | 创建运行并分析 |
| `GET` | `/api/agent/runs/:id` | 恢复运行 |
| `POST` | `/api/agent/runs/:id/clarify` | 提交澄清答案 |
| `POST` | `/api/agent/runs/:id/approve` | 批准、创建并验证 |
| `POST` | `/api/agent/runs/:id/track` | 刷新追踪 |
| `POST` | `/api/agent/runs/:id/commands` | 页面快捷操作的统一命令入口 |
| `POST` | `/api/agent/runs/:id/messages` | 模型规划受限意图并返回 Agent 回报、状态或字段变更提案 |
| `POST` | `/api/agent/runs/:id/confirm-action` | 确认或取消对话提出的状态或字段变更 |
| `PATCH` | `/api/agent/tasks/:id` | 更新 Local Task Hub 任务状态 |
| `GET` / `PUT` | `/api/user-skills` | 读取 / 保存用户 Markdown Skill |
| `GET` / `POST` / `DELETE` | `/api/config` | 查看、保存、清除运行时模型配置 |
| `POST` | `/api/config/test` | 测试模型连接，不保存配置 |

兼容接口 `POST /api/analyze` 仍保留，但前端主流程已经使用 Agent API。

## 7. 安全设计

- API Key 可保存到被 Git 忽略的本机配置文件或环境变量中，接口仅返回脱敏状态；该方案适合本机单用户原型，不等同于生产密钥管理；
- 用户输入不能覆盖系统安全规则；
- 外部写操作必须显式批准；
- 工具参数通过 Zod 校验，批准范围受原计划任务约束；
- 创建操作具备幂等键，成功后必须回读；
- 当前不提供删除外部任务能力；
- `.env`、JSON 数据文件、截图、构建产物、归档和本地视觉参考均不进入 Git。

## 8. 当前限制

- `Local Task Hub` 是本地连接器，不是真实第三方集成；
- JSON store 适用于单进程本地演示，不具备生产数据库的并发与迁移能力；
- API 尚无身份认证和多租户权限模型；
- 没有独立 retry API，失败恢复通过原审批载荷复用 `/approve`；
- 分析请求当前同步完成，`analyzing` 状态只在前端短暂显示；
- 对话支持澄清回答、进度查询、状态变更及五类任务字段修改提案和解释；仍不能任意新增 / 删除任务或仅凭自由文本直接审批创建；十套人工对话用例尚未全部运行；
- 解释性对话由模型根据运行上下文生成，尚未对回答文本做逐字段事实校验，不能等同于目标平台实时事实核验；
- 模型对解释性回答的事实一致性尚未逐字段自动校验；审批、验证和追踪仍由确定性状态机执行；
- 主 JavaScript 包尚未分包；
- 尚未基于大规模、人工标注的真实会议数据评测，不能声称模型准确率；
- 尚无真实企业用户、上线规模或生产稳定性数据。

## 10. 演示建议

演示时先使用缺少负责人和日期的纪要，在待处理事项和对话中展示同一澄清的解决过程；再进入统一审批，解释优先级理由并只批准选中任务；最后展示 `LTH-*` ID、回读验证、状态变更提案确认、活动记录和完成闭环。团队别名可用“老张 → 张三”单独演示。答辩中应明确说明写入目标是 Local Task Hub，真实第三方连接器尚未接入。
