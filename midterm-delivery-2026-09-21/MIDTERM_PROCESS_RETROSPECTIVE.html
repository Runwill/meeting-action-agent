中期制作过程中的问题与挑战

最大的困难不是把模型接入页面，而是把最初偏“一次性结构化抽取”的实现，重构成用户能理解、能控制、能核对结果的受控 Agent 工作流。

Executive Summary

首要问题是产品模型定义偏差。早期版本更接近“LLM 把纪要转成 JSON”，对话、澄清、审批、执行和追踪彼此割裂，因此后续经历了从脚本式处理到状态机 Agent 的架构重构。

最频繁的返工来自流程语义与界面不同步。例如已澄清内容仍显示待确认、逾期事件触发突兀、问题没有参考原文、写操作没有统一确认入口。状态正确并不代表用户能看懂或信任流程。

测试与汇报一开始更关注“有多少功能”，而不是一条真实会议流程能否成立。简单样例、分散截图和技术名词容易造成过度宣传；后期才补齐真实口语化纪要、证据链、隔离运行截图和验收边界。

中期版本已形成受控闭环，但智能效果尚未完成系统化评测。工程回归与浏览器 QA 已通过，真实第三方连接器、真实会议标注集评测和生产级凭据/数据能力仍属于后期工作。

架构返工的根源：最初做成了“会输出 JSON 的脚本”

早期实现把模型主要放在文本抽取入口，按钮和脚本直接承担后续状态修改。这样虽然能快速演示“纪要变任务”，但不具备完整的 Agent 生命周期：模型不理解当前运行状态，用户操作也没有统一经过意图判断、状态守卫、确认和回报。

会议纪要分析澄清审批执行回读验证追踪完成

采取的修正

建立状态机驱动的单 Agent 流程；页面快捷操作和自然语言命令进入统一运行时；模型负责理解和提出受限操作，确定性代码负责状态守卫、审批、幂等写入、回读和验证。

仍然存在的挑战

必须在“像 Agent 一样理解自然语言”和“不能绕过审批或错误写入”之间保持边界。当前方案有意限制任意增删任务、跨运行修改和自由文本直接审批，这属于安全设计，不应包装成无限自主能力。

用户配置一度被固定字段污染，Prompt Skill 分层后来才清晰

早期用户团队知识采用固定的结构化字段，难以容纳成员别称、行业术语、会议习惯和自定义优先级规则，也让用户误以为所谓 Skill 只是旧本地脚本的配置表。这里需要区分两件事：用户提供知识应允许自然语言，模型输出为了进入状态机仍然必须结构化。

采取的修正

用户上下文改为多份 Markdown Skill，自然语言描述“老张是张三”“上线阻塞项默认高优先级”等知识；系统 Prompt Skill 与用户 Skill 分层，用户内容不能覆盖审批、安全规则和工具权限。每次运行保存实际启用的 Skill 快照。

表达上的挑战

项目登记了 9 个版本化 Prompt Skill，但并非 9 个模块都逐一调用模型。实际分析注入 3 个模块，对话注入 2 个模块，其余流程由状态机执行。报告若直接写“九大智能模块”，会制造误解。

流程正确不等于用户能理解：澄清、优先级和事件都需要证据链

多轮体验问题暴露出同一个根因：后端状态、模型判断和界面文案没有共享同一套语义。用户不仅要知道“系统在问什么”，还要知道“为什么问、对应哪句原文、回答后改变了什么”。

主要问题、修正与当前状态

按产品流程整理，不按提交次数或页面组件罗列

测试难点不是增加文本数量，而是覆盖真实语境和失败路径

最初三个样例过短、彼此割裂，而且有的样例声称测试别称或澄清，实际对应配置和上下文却为空。随后虽然合并了综合输入，但又暴露出“会议纪要写得太规整”的问题。最终才形成两种同测试点输入：结构化综合纪要和多人逐句发言、插话的口语化记录，同时保留 13 套独立回归用例用于定位失败。

目前覆盖的关键场景

完整任务、模糊候选、人员别称、负责人不明、日期缺失、优先级冲突、依赖与风险、非任务讨论、人工审批、回读不一致、状态变更和完成闭环。

不能越界的结论

47 项自动化测试主要证明状态机、接口和边界行为，模型调用使用可控 mock；真实 DeepSeek 只完成了若干隔离冒烟路径。十套对话人工样例尚未全部逐项执行，也没有大规模人工标注的真实会议数据，因此不能宣称任务识别率或澄清准确率已经达标。

演示环境和 UI 可见性本身也是工程交付

本轮多次出现“代码里已经有功能，但用户实际看不到或无法稳定使用”的问题：后端没有启动导致 API 配置保存失败、空响应被前端当 JSON 解析、顶栏滚走、下拉菜单打开后页面滚动条消失、移动端遮挡，以及通透度控制面板被定位到视口外。这些问题说明仅检查组件存在或接口通过远远不够。

采取的修正

启动脚本分别检查前端与 API 服务，前端安全处理空响应；完成桌面、390px 和 320px 的实际浏览器 QA；对自定义菜单、弹窗滚动、常驻导航和浮层定位进行复核；截图使用隔离数据运行，避免污染用户存储。

持续挑战

当前本机单用户演示依赖两个服务进程和本地文件持久化。运行可靠性已经改善，但仍不等于生产部署、并发数据存储、认证或多租户能力。

报告和 PPT 也经历了“功能堆砌”到“证据叙事”的返工

早期材料存在 AI 套话、空泛后期目标、把内部模块数量当成果、截图按单个状态重复计数，以及示例人物和真实实现不一致等问题。后续将材料集中到同一交付目录，按功能证据链组织截图，并明确 Local Task Hub、真实模型冒烟和工程测试各自能证明什么。

已经形成的汇报原则

围绕开题提出的三个核心问题组织证据：AI 提议优先级与人工审核、人员别称理解、人员与任务关系不明确时的主动澄清。后期目标只突出真实任务平台连接器和效果指标，不用没有验收标准的工程名词填满页面。

后续最值得优先解决的两项工作

  1. 接入一个真实任务平台。沿用当前已验证的审批、幂等和回读协议，补充实际授权、字段映射、错误处理和恢复路径。只有这一步完成，才能验证 Local Task Hub 抽象是否真正可迁移。
  2. 建立真实会议效果评测。准备脱敏、人工标注的会议样本，分别统计任务识别、负责人/日期抽取、别称归一、澄清必要性、优先级建议和端到端写入成功率；把模型质量与工程流程测试分开报告。

复盘后仍需回答的问题

  • 真实任务平台最终选择哪一个，其字段模型与当前 Local Task Hub 有多少差异？
  • 澄清质量如何评价：问题数量越少越好，还是信息补全率与用户操作成本共同衡量？
  • 对话解释发生事实偏差时，是否需要逐字段引用运行数据，而不是允许模型自由组织全部内容？
  • 十套人工对话样例应在何种固定模型版本和参数下执行，才能形成可复现基线？
